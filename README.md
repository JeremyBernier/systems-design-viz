# System Design Simulator

Interactive 3D visualization of a small web service under load: clients → load balancer → web servers → cache / database, plus a job queue with workers, and an analytics side fed by Kafka: a lake writer committing Parquet files to an S3 + Iceberg data lake, ClickHouse for real-time queries, Trino for SQL on the lake, and dashboards querying both.

```
npm install
npm run dev
```

- Drag the traffic slider (20 → 20,000 req/s, log scale) and watch bottlenecks appear, backlogs grow and nodes explode.
- Click any component to select it: it is highlighted and its live metrics open in the side panel. Press **Zoom in** there (or double-click the component) to look inside — the queue, database and functions have an internals view, and every component has a hardware view of CPU, memory, storage and network. `Esc` zooms out, then deselects.
- **System** presets (YouTube, Instagram, Uber, a job scheduler, a simple web app) reconfigure components, technologies and traffic.
- **Trade-offs**: every component's panel lists what its current technology gains you and what you give up, and how much work it is to run. **Compare all options** opens a side-by-side table of every alternative (cost at today's load, what one unit handles, how it grows, how it fails, effort to run) above a chart of monthly cost against load, so you can see where the cheapest choice flips. The trade-off text is in `src/tradeoffs.js`; the costs come from the same price functions as the bill.
- **Names**: each component is named for the job it does in the chosen system ("Transcoding Workers", "Feed Cache", "Rides DB"), with its technology underneath. Names come from a preset's `names` entry in `src/presets.js`. Web servers are interchangeable replicas of one service, so they share a name and a number ("Video Service 3"), and the number is dropped when only one is left.
- **Build**: press **Build** under the header (or `B`), pick a component from the dialog, and it follows the pointer as a preview until you click to build it there (`Esc` cancels). Drag components around, and use *Connect components* to wire sensible pairs together. Click a component to change its technology (e.g. PostgreSQL → DynamoDB, EC2 → Lambda), toggle its connections or remove it.
- **Traffic patterns** shape the slider's rate over time: a daily cycle (one day per 2 minutes, slider = evening peak, trough at ~30% of it), a launch-day ramp, and a flash crowd (5× within seconds, fading slowly). The 6-second spike button still works on top.
- **Autoscaling**: the web tier uses target tracking on average CPU (min / max servers, target %); workers scale on queue backlog per worker. New capacity is not instant — an EC2 or Compute Engine VM takes ~18 simulated seconds to come into service (≈3 min in real life), Fargate ~6 s, Kubernetes ~4 s, while Lambda and Cloud Run scale at once and pay a cold start instead. Scale-in waits for 15 s of low load and removes one server at a time. The cost breakdown shows the average over the last cycle, so an autoscaled fleet can be compared with one sized for the peak.
- **Reliability**: the header shows p50 / p99 latency and an SLO tile (availability over the last 60 s, error budget left, burn rate). Set the client timeout, the retry policy (off, naive, or backoff + jitter + a 10% retry budget) and the SLO targets in the left panel. Responses slower than the timeout count as errors, and retries add to the load: with naive retries a traffic spike becomes a retry storm that outlasts the spike. Percentiles are derived analytically (log-normal service time, M/M/c queueing delay, mixture of cache-hit / miss / write paths) — see `src/latency.js`.
- **Content delivery**: images, scripts and video are requested separately from API calls, served by a CDN and stored in object storage. Each system has its own asset profile (YouTube and Instagram are almost all media bytes). Change the average asset size or the CDN cache TTL, or remove the CDN and watch the load balancer's link and the web servers' network cards fill up and "Data transfer out" take over the bill.
- **Data tier scaling** (Architecture panel): *read replicas* take reads only and must replay every write, so they do nothing for a write-heavy load and fall behind (replication lag) when pushed; *shards* multiply read and write capacity, less a penalty for cross-shard queries and the hottest shard; with a replica, a dead primary is replaced by *failover* in tens of seconds while reads continue; *cache nodes* add lookup capacity and memory, and losing one empties only its share of the keys. Engines that scale out by themselves (Cassandra, DynamoDB, Bigtable, Spanner) ignore the replica and shard controls. The model and its constants are in `src/datatier.js`; per-engine numbers are in `src/tech.js`.
- **Database guide**: select the database or the OLAP database and press *Compare databases and their tradeoffs*. It puts every engine in the catalog side by side (what it is good at, what you give up, and what the simulation assumes about it, with a button to switch to it), explains the concepts behind the differences (OLTP vs OLAP, data models, where writes go, consistency, B-tree vs LSM, who runs it), each with an experiment to try, and ends with ungraded "which would you pick?" scenarios. Content is in `src/dbguide.js`; its numbers are read from `src/tech.js`.
- **Numbers to know** (left panel): the latency ladder, how big one machine can be, what each machine in the simulator handles (read live from the model), estimating shortcuts, and a quiz. Quiz rounds draw 8 questions; the estimation ones use fresh numbers each round and compute their answers in code. Content and sources are in `src/numbers.js`.
- Estimated monthly cost is shown in the header, with a per-component breakdown in the right panel. Prices are ballpark public list prices (on-demand unless you pick a commitment) and live in `src/tech.js`.
- Deep links: `?preset=uber&traffic=5200&web=4&db=dynamodb&olap=snowflake&queries=120&compaction=0&focus=db&t=20` (`t` skips ahead N simulated seconds).

Modelling your own system:

- **Workload assumptions** (left panel, collapsed): request + response size, warm cache hit ratio, share of requests that enqueue a job, event size, bytes stored per write, app time per request, and requests/s per server and jobs/s per worker. They are ordinary `Sim.params` (`reqBytes`, `cacheHitRatio`, `jobFrac`, `eventBytes`, `writeBytes`, `svcTime`, `webRps`, `jobRate`) whose defaults live in `WORKLOAD` in `src/sim.js`; a preset may override them with a `workload` entry. The default `writeBytes` is deliberately inflated so a disk fills while you watch — set a real figure (≈1 kB) for your own system.
- **Plan from users** opens a capacity planner: daily active users, requests per user, peak-to-average ratio, write mix, data per write and retention go in; average and peak req/s, read and write QPS, storage growth, bandwidth and cache memory come out, with the arithmetic shown. It then sizes the technologies currently in the diagram (web servers at a target utilisation with N+1, database load and disk life, workers, event-stream headroom) from the same capacities the simulation uses. *Apply to simulation* sets traffic to the peak, the write mix, server and worker counts and bytes per write, and lists anything the simulator cannot represent (for example more than 6 web servers) instead of silently clamping.
- **Pricing** (above the cost breakdown): on-demand, 1-year (~30% off) or 3-year (~50% off) commitment, plus spot for worker VMs (~65% off). Discounts apply to instance-hours only — never to per-request, per-GB, storage or licence charges.
- **Copy link**: the address bar always holds a link that rebuilds the current system. On top of the readable params above it carries only what differs from the preset: `p=writePct:45,reqBytes:5000` (any other `Sim.params` value), `off=`/`on=` (components removed/added), `cut=web0.cache` / `wire=` (connections). Component positions and live state (backlogs, disk fill) are not saved.

Code: `src/sim.js` (rate-based simulation, no rendering), `src/cdn.js` (static asset traffic: CDN, object storage and the no-CDN fallback), `src/autoscale.js` (traffic patterns, autoscaling policies and their constants), `src/latency.js` (latency percentiles, client timeouts and retries, SLO), `src/datatier.js` (replicas, shards, failover, cache cluster), `src/tech.js` (technology catalog, logos, prices, pricing models), `src/presets.js`, `src/cost.js`, `src/planner.js` (capacity planner, pure functions), `src/share.js` (state ↔ URL), `src/scene.js` (Three.js), `src/ui.js` (panels and charts), `src/modelui.js` (workload, pricing and planner UI).
